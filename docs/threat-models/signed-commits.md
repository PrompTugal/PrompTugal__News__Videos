# Threat model: signed commits (scripts/check-signatures.mjs, team/keys.json, release.sh, the workflow)

> videos.b@PrompTugal.dinis, 19 November 2026. For review by security@PrompTugal.dinis. Licence: CC BY 4.0.

## What it is
Every commit to this repository is signed, as a git SSH signature, by the agent named in its `Agent:` trailer, with the key that agent published in `team/keys.json`, and names in `Claude-Session:` the session published with that key (Dinis Cruz, 18 and 19 Nov 2026; the guidance's section 2). The check is adapted from data.b@'s (PrompTugal__News__Data f68beb3, Apache-2.0), hardened after this wake's security pre-review. It runs in `release.sh` before every push and inside the rebase-and-push loop, and in CI on the range from the last release tag. One failing commit fails the range, and CI then deploys nothing.

## The key
- Ed25519, made with ssh-keygen in this agent's own cloud session on 19 Nov 2026, kept outside the repository (a folder of mode 700, the key file 600), with no passphrase: the container is the session's own and is reclaimed with it.
- Only its public half is published, as a PEM block in `team/keys.json`, with the agent and the full session URL. The check derives the OpenSSH form itself, so no SSH key line is in the repository, and the leak scan fails any such line anywhere.
- The signer is set for this repository only (`git config --local`: ssh-keygen and this key), because the environment's global signer signs with the environment's key.
- A new session cannot sign with this key. It adds its own in a commit signed by a key already listed, or Dinis adds it; at hand-over this entry is removed. If no listed key is left, only a person can add one, and until then CI fails: that is the recovery path, by design.

## What could go wrong, and the mitigations
| Threat | Mitigation |
|---|---|
| A commit that adds its own key | Each commit is checked against its parent's `team/keys.json`, never its own; only the one commit that first added the check (found in the trusted base's history once it holds the check) uses its own tree. |
| An unrelated history brought in by a merge | Every commit with no parent fails, except the trusted base, recorded in the check by its full id (de181efb94e19b731def28690a481f1c7ac76a11, the commit that turned signing on; security@'s control 6). |
| A shallow checkout hiding part of the range | Refused (control 6); CI fetches the whole history. |
| A push that edits the check | The check runs from the anchor's copy (the head commit of the last successful push run of the Pages workflow on dev), never from the commits it checks (control 7); never from the pushed tree, so a base without a check is refused. The test shows that a copy run from outside ignores a weakened check in the commits; that release.sh and the workflow take the base's copy is in their code, not in a test. The push that brought controls 6 and 7 was itself checked by the previous copy; they apply from the next push. The workflow file itself still comes from the pushed tree: only branch protection with a required check closes that, which is Dinis's to set. |
| Deleting the check | Commits are skipped only as ancestors of the first commit, so a later commit without the check is still checked. |
| A revoked or rotated key | Matched by its fingerprint, not its name; revoked by removing it from the keys file (a "superseded" entry is not used, since a commit date can be set by anyone); a key must also still be listed at the tip of the range, so it cannot come back through a branch that started before its removal. A key listed twice makes the file unusable. |
| A principal that widens the allowed signers | Principals must be plain addresses. |
| Two agents or sessions in one commit | Exactly one `Agent:` and one `Claude-Session:` trailer, compared exactly with the key's. |
| A name that looks like CI's | Nothing is exempt: CI makes no commits here, only tags. |
| Something hidden in a public key block | Each block in a keys file must parse as a public key. |
| Pushed code tampering with the checks in CI (control 9, fifth ruling) | The signature, trailer and leak checks run in their own job, `checks`, which runs no pushed code: it checks out the pushed tree as data, receives the built site only as the Pages artifact deploy publishes (unpacked as data, links refused), takes each checker from the anchor's tree, refuses a link at the checker path, and runs it with an absolute node, `NODE_OPTIONS` cleared and replaced objects ignored. GITHUB_ENV and GITHUB_PATH are per job, so what the pushed build writes there never reaches it. Deploy and the tag need it. The build job runs only the functional gates (build, validator, the pushed copies' tests). Not tested in a real run of Actions here: the first push of this change is that test. |
| A workflow without the security job becoming the anchor (live.b@'s a4c6fce) | The anchor's run must also have a job named `checks` that passed, checked through the run's jobs, not only its conclusion (CI and release.sh). A workflow that keeps the name but weakens the job is closed only by branch protection. |
| A pushed `_site` link steering the download (live.b@'s a4c6fce) | The artifact lands in RUNNER_TEMP and is vetted there; a pushed `_site` path is refused and pushed `.gitattributes` files are removed before anything is downloaded. |
| A manual run on another branch deploying (live.b@'s a4c6fce) | The checks, deploy and tag jobs run only for `refs/heads/dev`. |
| A hostile Pages artifact (events.b@'s 188bcf8) | Its listing is vetted before unpacking (plain files and directories only, no absolute path, no `..`); it is unpacked before any trusted copy exists, and checked for links again. |
| Files the leak scan could miss (library.b@'s LIB-2026-067) | A file with a NUL byte is still scanned for the exact secret shapes (only the entropy rule is left out); a symbolic link is never followed and is reported. |
| Pushed config steering the checks (signals.b@'s 75a59d0) | A changed `scripts/commit-exemptions.json` is refused; `.gitattributes` cannot act, because `git show` and `git diff` of trees apply no filter or textconv without config in `.git/config`, which is not pushed; the keys come from the parent's `team/keys.json` by design. The leak scan's pin exemption compares with the vendored bar files in the pushed tree, so a push could only hide the three fingerprints of its own files. |
| A push that weakens another security check | Every security check release.sh and CI run comes from the trusted base's copy (security@'s control 7, widened): the signature check, the trailer check (check-commits.mjs), the leak scan with its exemptions, and in release.sh the sites bar's pin check. Each copy is written into scripts/ under an ignored name (scripts/trusted-*.mjs; anything left at that path, a link included, is removed first) and removed after, pass or fail; a base without one is refused. In CI they run in the `checks` job, which runs no pushed code (control 9), and the leak scan reads the very Pages artifact deploy publishes; in release.sh the leak scan runs after the build it scans; and `NODE_OPTIONS` is cleared and replaced objects ignored. What they still read from the pushed tree: the trailer check's `scripts/commit-exemptions.json`, which a push may not add or change (refused), and the sites bar's vendored files, which the pin check compares with the live registry. The workflow file and release.sh themselves come from the pushed tree, which only branch protection closes. The build, the validator and the tests stay on the pushed tree (functional gates). Skips are decided only by ancestry of the trusted base (control 8; the test that deletes the check and adds an unsigned commit fails). There is no override of the trusted base. |
| Where the checker comes from, and the range (security@'s sixth ruling) | The anchor: the head_sha of the newest run of this workflow file, on dev, from a push, that concluded success, read from GitHub's API (CI with its own read token, actions: read; release.sh without one, the repository being public); every field is checked, not only the query. Only GitHub Actions creates runs, so unlike a deployment record (which anyone with write access can make) a pusher cannot fake one; a pushed rewrite of the workflow file is still the known gap, closed only by branch protection, Dinis's to set. The anchor must be in the clone and an ancestor of the head, or the run fails; the range is anchor..head, so a dropped push's commits are covered; every check and its config come from the anchor's copy; tags and BEFORE are not used; a manual run anchors the same way. |
| Replaced objects or grafts | The check runs with `GIT_NO_REPLACE_OBJECTS=1`. |
| A tag moved to hide commits from CI | Tags are not used by the checks; protecting the `v*` tags and the branch is still Dinis's to set (asked in status.json). |

## Trust between listed keys
Every listed key is trusted to sign for its own agent and to add or remove keys in later commits: the listed keys trust one another. Today the only key is this agent's.

## Tests
`scripts/test-check-signatures.mjs` (26 cases, each failing case asserting its reason, in throwaway repositories with throwaway keys and `gpg.ssh.program=ssh-keygen`) and `scripts/test-leak-scan.mjs` (the SSH line and key block rules), run by release.sh and CI.
